# ゲーム画面再現のデザイン・UI設計監査

調査日: 2026-10-04  
対象: `Title/setting/screens/` のタイトル・システム・サウンド・セーブ/ロード画面、プレイ中メニュー、画面HTML/CSS編集機能、およびBrowser/Nativeの共通描画経路。

## 要約

現状は、参考画面の大枠（画面遷移、タイトルのメニュー、設定値、セーブスロット、サムネイル、ゲーム中メニュー）を実際に操作できる共通UIとして構成できている。一方、商用ノベルゲームの画面を「同じ設計思想のまま自由に再現する」段階には達していない。最大の制約は、HTML/CSSを受け付けることと、ブラウザ相当の自由なレイアウト・描画ができることを混同しやすい点にある。実際の実行契約は、安全なHTML/CSSの一部を中間画面ツリーへ変換し、Browser DOMとSDL Nativeが別々に描画する限定的なUIシステムである。

したがって問題は単にCSS機能の不足ではない。画面のレスポンシブ設計、共通部品、入力状態、動的データ、編集ワークフロー、ネイティブ描画差、仕様書の正本が互いに独立して制約されている。個々の装飾プロパティを追加するだけでは、画面を作るたびに座標・状態・移植性を手作業で調整する構造が残る。

| 領域 | 今できていること | 再現上の限界 |
|---|---|---|
| タイトル | 背景画像、画像・文字ボタン、hover/focus、Continue/Start/Load/System等の操作 | 状態ごとの演出、複雑な合成、動的なボタン状態・アニメーションは弱い |
| システム | 設定値の切替、スライダー、ショートカット変更、保存可能な設定 | 右クリック割当ては未対応で、画面にその旨を表示する。密な画面を固定座標で構成 |
| サウンド | master/BGM/SE/voice等の音量・mute、キャラクター別volume設定 | 参考画面のキャラ一覧は12枠相当だが現行サンプルは2人分を手書き。動的生成・スクロール設計がない |
| セーブ/ロード | ページ、スロット、状態、サムネイル、ロード可否、操作 | カードの高密度な可読性、可変情報量、長文、解像度変化、ブラウザとNativeのサムネイル一致に注意が必要 |
| プレイ中メニュー | 固定のレイヤー上に背景・動画・キャラ・画像・会話UI、右側メニューを重ねられる | 任意UI合成や画面別の自由な配置・アニメーションはまだ限定的 |
| エディタ | テンプレートをプレビューし、HTML/CSSソースを編集 | テンプレートがある画面は「HTML/CSSが正本」となり、ボタン追加とドラッグ配置が無効。画面上の直接編集がない |
| 配布先互換性 | 共通ツリーをBrowser/Nativeで利用し、対応範囲をコンパイル時に制限 | 描画エンジン・フォント・標準コントロールが別物で、ピクセル一致を保証しない |

## 重大度の高い問題

### P0 — 見た目が操作可能性を偽る（解消）

`Title/setting/screens/system.html` の「サブクリックの機能」は、`<span>` と文字の `□` / `◉` で描かれた静的一覧で、操作できる設定に見えていた。2026-10-04に一覧を取り除き、右クリック割当てが利用できないことを示す説明へ置き換えた。操作できるという誤解は解消したが、右クリック機能の割当て自体は未実装である。

### P0 — CSSの受理と描画意味が一致しない

画面文書コンパイラには安全性のためのCSS許可リストと、両描画器で共有できる機能の制限がある。一般ブラウザで有効なCSSでも、コンパイル時に拒否されるか、レイアウト木へ正しく反映されない場合がある。監査時点では `vw` / `vh` が単位を外した数値をpx相当として扱う不一致があったが、本Goal中に再現テストを追加して修正した。現在は基準キャンバス寸法から共通画面ツリー生成時にpxへ正規化し、1280×720における `10vw=128px`、`10vh=72px` を回帰テストしている。

対応はプロパティの追加ではなく、プロパティごとの「構文受理・意味計算・Browser描画・Native描画・編集プレビュー」を一つの適合表とテストで結ぶこと。未対応値は誤解を招く形で受理せず、対象ファイル・セレクタ・プロパティつきで拒否する。

### P1 — テンプレート編集がソース中心で、視覚編集が切断される

`Edit/editor.js` の画面エディタは、テンプレート画面を検出するとHTML/CSSを正本として扱い、`ボタンを追加` を無効化する。テンプレート編集時のインスペクタはHTML/CSSのtextarea中心で、プレビュー上の要素を選択して配置・サイズ・重なり順を調整する操作がない。つまり「自由な画面を作るためHTML/CSSに移行すると、非プログラマ向けの配置編集を失う」という設計上の断絶がある。

必要なのはHTML/CSSを排除することではなく、ソースと視覚編集が同じ文書モデルを編集する仕組みである。選択中要素のアウトライン、ドラッグ移動・リサイズ、数値インスペクタ、部品ツリー、ソース位置との同期が必要。視覚エディタが別形式を生成してHTML/CSSと二重管理になる方式は避ける。

### P1 — 固定キャンバスと絶対座標が画面密度を固定する

`Title/setting/player-ui.json` が1280×720の論理画面を定め、`game-screens.json`のcanvasはそこから導出する。`shared.css` は画面ごとにabsolute座標・幅・高さ・z-indexを多数指定している。デザイン再現には有効だが、ウィンドウ縮小、異なる縦横比、文字拡大、長い翻訳文、セーフエリアに対して各部品が再配置されない。`contain` では余白が出て、`cover` は切り抜くだけで再レイアウトしない。二列のシステム画面や右側操作パネルでは、幅が足りないと重なり・切れが起きうる。

基準解像度だけを変えるのではなく、共通部品に制約ベースの配置（アンカー、余白、最小/最大、折り返し、スクロール領域）を持たせ、狭幅時の代替レイアウトを定義できる必要がある。現在の共通レイアウト木は限定的なabsolute/flex/gridであり、完全なブラウザレイアウトではない。

### P1 — BrowserとNativeの見た目を同等と誤認しやすい

画面HTML/CSSは共通ツリーに変換されるが、BrowserはDOM、NativeはSDL描画である。文字のラスタライズ・フォントフォールバック・標準スライダー/チェックボックスの形・フォーカス表示・DPI・OSウィンドウ合成は一致しない。`RENDERING-COMPATIBILITY.md` も、エディタプレビューだけではNativeの視覚受け入れを証明しないと明記している。

商用品質を目指すなら「CSSを両方で同じように解釈する」では足りず、見た目に重要なボタン・スライダー・タブ・スクロール領域等は共通の独自描画部品として描画と入力を定義する必要がある。許容差を決めたBrowser/Nativeのスクリーンショット比較も不可欠。

## 画面ごとのデザイン・操作上の課題

### タイトル

- タイトル画像、背景、左側メニュー、複数の選択肢という骨格は再現可能。ボタンはテキストでも画像でも構成でき、hover/focus用の簡単な見た目変更ができる。
- 参考画面のようなタイトルロゴと背景美術の一体感、半透明帯、選択時の発光・移動・フェード、BGM同期演出は、CSSの限られた状態と描画機能だけでは表現しにくい。細かな装飾は画像化で回避できるが、文字差替え、翻訳、解像度対応、フォーカス状態と衝突する。
- Continue不可などの状態は操作側の無効化が必要。単に同じボタンを表示して押しても何も起こらない状態では、視覚的なdisabledと実操作がずれる。
- title画面のキー操作、マウス操作、キーボードフォーカスの順序と現在位置の強調を画面設計上の契約として統一する必要がある。

### システム

- 参考画像の二列・高密度レイアウトを固定座標で似せられる一方、説明文と操作部品の高さ・文字サイズが窓サイズと独立している。日本語以外の長文や文字拡大に弱い。
- 複数の選択ボタンで選択済み状態を表現しているが、全画面で共通のselected/disabled/pressed状態スタイルを部品単位で管理する仕組みは限定的。
- ショートカット変更は循環選択式であり、任意キー割当、重複割当の説明、修飾キー、競合検出などを自由に見せる一般的な入力割当UIではない。
- 右クリック機能の割当ては未対応であり、設定画面では未対応であることを説明する。割当て機能自体は引き続き不足している。
- 設定項目の説明、現在値、初期値、保存先を同じスキーマから作る仕組みが弱く、HTML上の表示と実行時設定許可リストの二重管理になりやすい。

### サウンド

- master/BGM/SE/system SE/voice等のスライダーとmute、会話欄透明度などを設定値に接続できる。画像を使ったつまみ等も共通対応領域内なら作れる。
- 現在のキャラクター音量欄は `sound.html` に個別パネルを固定記述する方式で、サンプル設定にも`ayaka`と`sister`の2人だけが列挙される。キャラクター追加時にHTML/CSSと設定キーを手で増やす必要がある。参考画像のような多数のキャラ音量パネルを一般化できていない。
- 12人以上を並べるデザインでは、画面高不足時のスクロール、ページ切替、検索、名前の長さ、立ち絵なしキャラの扱い、同一人物の別名、追加/削除に対する再配置が未解決。
- 音量目盛り、現在数値、mute時にスライダーをどう扱うか、キーボードでの増減、読み上げ可能なラベルを一貫させる必要がある。

### セーブ/ロード

- 現行テンプレートは12スロット、ページ切替、サムネイル、シーン/本文/時刻等の項目、empty/ready/corrupt/incompatible状態を扱う。基本的な保存・ロード操作を単なる絵ではなく共通アクションとして持つ。
- 参考画面のカードはサムネイルと文章が混在する。現在のカード寸法・固定フィールドでは長いシーン名/本文や翻訳によって切り詰められ、情報の優先順位を画面ごとに調整しづらい。
- 3列×4行の固定配置はスロット数や画面比率を変えるとCSS再設計が必要。ページ数とslot数の間にデータ契約はあるが、可変カードテンプレート一般ではない。
- Browserはストーリー要素を独自Canvas合成してサムネイル化し、Nativeは最後に描画したSDLフレームをキャプチャする。このため、特殊な画面CSS・フォント・効果のある場面ではサムネイルが再生画面と一致しない可能性がある。保存画面そのものを除外する仕様は共通だが、合成方式は同じではない。
- サムネイルの欠損とセーブ本体の可用性を分けている点は適切。表示失敗がロード失敗に波及しない保証を継続して確認する。

### プレイ中メニュー／会話UI

- 背景・動画・キャラクター・画像・会話欄などの定レイヤーを持ち、シナリオ側で `move`、カメラズーム、会話欄表示切替、背景遷移等を記述する方針は、物語演出をコード側で合成する目的に沿っている。
- これは任意のUIレイヤーを好きな順に作る仕組みではない。固定レイヤーの順番を越える合成、任意画像のモーション対象化、複数背景を任意枚数保持する構成などは制約される。背景揺れのようにシナリオで行う演出も、現状の `move` の対象種別・同期モデルが表現できる範囲に限られる。
- カメラズーム、背景切替、動画半透明、会話欄表示切替を個別機能として足すだけでは、同時に動く複数対象のタイムライン、イージング、キャンセル、シーン遷移中の状態継承は統一されない。演出が増えるほど「命令ごとの例外」にならないよう、時間・対象・補間を共通のモーション意味論にする必要がある。
- 動画を含む場面は、動画再生中に後続物語の入力・音声・当たり判定が進まないよう、描画だけでなく実行状態も一時停止/専有する契約が重要。

## 共通部品・データモデルの不足

現在の安全なHTML/CSSテンプレート方式には利点がある。任意JavaScriptを禁止し、固定アクション語彙と許可済み設定キーだけを結びつけるため、ゲームの状態を書き換える自由コードを画面へ埋め込まずに済む。画像ボタンや保存スロットのデータ差し込みも可能である。

その安全境界の一方で、画面作者が必要とする一般部品とデータ駆動能力が足りない。

- 部品: button, tabs, slider, checkbox以外に、radio group、scroll/list、select、key binding、tooltip、modal、progress、音声テスト、確認ダイアログなどの意味付き共通部品が不足。
- 状態: hover/focusはあるが、pressed、選択中、無効、処理中、エラー、トグル、ゲームデータに応じた表示条件を横断的に扱う状態モデルが薄い。
- 繰返し: セーブスロットのような特別な繰返しはあるが、キャラクター音量や実績など任意データ集合のlist/repeatはない。
- レイアウト: 共通キャンバスの固定配置に寄り、制約レイアウト・スクロール・折返し・レスポンシブ切替が足りない。
- 表現: 9-slice、画像アトラス、状態別disabled/focus資産、マスク/クリップ、transform、shadow、transition等が不足または非共通。ボタン画像の簡易差し替えはできても、商用UIでよくある伸縮可能な枠飾り、状態遷移、光彩等を汎用化しづらい。
- アクセシビリティ: DOMとNativeでフォーカス/読み上げ挙動が異なり、ARIA相当の意味、読み上げ順、コントローラー操作、色以外の選択表示、文字拡大への対応を共通仕様として保証していない。
- ローカライズ: 固定pxと固定高さ、画像に焼き込まれた文言は翻訳で破綻しやすい。フォントの選択と埋込みもBrowser/Native共通の保証がない。

## エディタとランタイムをまたぐ作業上の難点

1. 作者はHTML/CSSを書けば自由だと思いやすいが、実際には共通ツリーへの変換後に対応する部分集合だけが動く。
2. プレビューがBrowserであるため、SDL Nativeでの文字幅・標準部品・DPI差を編集時に発見できない場合がある。
3. テンプレートの本格化により、従来の要素追加/座標編集とソース編集が別モードになった。GUI操作を残したまま自由記述を増やす中間的なドキュメントモデルが必要。
4. CSSとHTML、画面設定JSON、UI設定キー許可リスト、Browserアクション、Nativeアクションを追跡しないと、見た目だけ存在する設定や未接続の値を作れてしまう。
5. 同じ画面のテーマ、部品寸法、余白、色、フォント、操作状態を個別CSS値で重複指定している。デザイントークン/テーマとコンポーネント規約が必要。
6. 基準画面サイズのスクリーンショットが似ていることと、他サイズ・Native配布版・キーボード操作が正しいことを区別しにくい。

## 仕様・ドキュメント上の注意点

- `docs/editor-project-overview.md` は画面仕様の全体像を説明するが、`Title/setting/screens/RENDERING-COMPATIBILITY.md` のような実装制限とセットで読まないと、CSS互換性を過大評価する。
- セーブサムネイルの説明に、画面要素の列挙が省略された記述と、Browserの実際の合成対象を列挙した記述が併存する。共通仕様として「保存するフレームに何を含めるか」を一箇所で定義し直す必要がある。
- ブラウザ一般のHTML/CSSと、Novel Scriptのscreen HTML/CSS subsetの区別を、エディタとヘルプの入口で明示すべき。
- `vw/vh` のように「構文で受理されるが意味が違う」ケースは、互換性ドキュメントだけでなくコンパイラの適合テストへ結び付けるべき。

## すでに良い設計基盤

- 画面とシナリオを分離し、HTML/CSSファイルをsettingフォルダに置く構成は、作品ごとに画面を所有する目的に合う。
- 任意JavaScriptを許さず、許可されたaction/settingだけを接続する設計は、Native移植・安全性・セーブ互換性を維持しやすい。
- 共通中間画面ツリーをBrowser/Native両方へ渡す方針は、適合性テストが伴えば有効な抽象化である。
- セーブスロットの状態をempty/ready/corrupt/incompatibleに分け、ロード可能性をUIと実処理で合わせること、サムネイル欠損だけでセーブを失効させないことは良い契約。
- 画像ボタン、背景、アイコン等を作品素材として置き換えられるため、既定テーマだけに固定されていない。
- 画面編集にアスペクト比プレビューがあり、Browser専用実装を共通機能と誤認させない互換性文書が存在する。

## 優先して解く順序

### 1. 意味論と互換性の正本を固める

HTML/CSSプロパティ・セレクタ・部品・状態・データバインドを列挙し、各々に parser / layout tree / Browser / Native / editor preview / test の対応を記録する。`vw/vh` 等の不一致を解消し、未対応機能は明確に拒否する。

### 2. UIを意味付き部品として増やす

画面ごとの独自HTML断片を増やす前に、Button、Toggle、Range、Tabs、ScrollList、SaveSlot、KeyBinding、CharacterVolume等の共通部品について、見た目・操作・値保存・キーボード/コントローラー・状態を一つの仕様にする。ユーザーデータ集合に対する安全な繰返し表示を追加すれば、キャラクター音量の手書き2枠問題を解消できる。

### 3. ソースと直接操作を同じ木に接続する

画面プレビューの要素選択・ドラッグ・サイズ変更・整列・前後移動を共通ツリーへ反映し、HTML/CSSと即時同期する。片方から編集できない二つの画面定義を作らない。

### 4. レイアウトとテーマを導入する

ピクセル固定の完全廃止ではなく、自由配置を残しながら、アンカー・コンテナ・余白・折返し・スクロール・ブレークポイント・セーフエリアを追加する。色・寸法・文字・状態をテーマトークンにし、作品ごとの外観変更を重複値なしで行えるようにする。

### 5. 両描画器を実画面で検証する

各公式画面について複数比率・複数DPIのBrowser/Nativeキャプチャと画素差/領域差テストを持つ。フォント、ボタン状態、範囲入力、サムネイル、文字長、フォーカス移動は別々に検証する。Editor preview合格だけで出荷可と判定しない。

### 6. 実際の参考画面を受け入れ基準にする

タイトル、システム、ロード、サウンド、プレイ中メニューごとに、参考画像と同じ解像度で次を確認する。

- 外形・余白・整列・文字階層・コントラスト
- hover / focus / selected / disabled / pressed
- キーボードとマウスによる全操作
- 空/満杯/破損/非互換セーブ等の状態
- 長文・文字拡大・別ロケール
- 画面比率変更、Native実行、ウィンドウ/DPI変更

## 評価範囲と未確認事項

このレポートはソース、画面定義、互換性仕様、既存テストの対象範囲を調べた設計監査であり、全OS・全DPIでのピクセル比較や、すべての画面操作を今回あらためて実機で網羅した結果ではない。既存テストが通ることは挙動契約の確認にはなるが、参考画像との商用品質の一致を証明しない。特にSDL Nativeの実画面、フォントフォールバック、実ウィンドウの縮小・拡大について、継続的な視覚受け入れテストが必要である。
